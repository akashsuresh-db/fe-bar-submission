# Reference Architecture — Lakebase Operational Data App (CURRENT)

> **Version:** `v2026.07` (live).
> **Archetype:** operational "data app" — a Databricks App backed by Lakebase Postgres over the lakehouse.

A transactional front end sits on **Lakebase** (managed Postgres) for low-latency application state,
with the governed lakehouse behind it for analytics and ML. A demo binds here when the headline is an
**interactive application** — write-back, session/OLTP state, sub-second reads — rather than a pipeline,
dashboard, or model in isolation.

## Pattern

A **Databricks App** serves an interactive UI. Operational reads/writes go to **Lakebase** (Postgres)
for millisecond latency and transactional state; analytical and ML workloads run against Unity
Catalog / Delta. Data syncs between Lakebase and the lakehouse so the app's operational state and the
governed analytical copy stay coherent. The app calls governed endpoints (SQL, Model Serving, Genie) as
needed.

The architectural physics: analytical stores are not built for high-QPS transactional access, and
lakehouse tables are not built for row-level OLTP. Lakebase gives the app a Postgres-native operational
tier while Unity Catalog remains the governed system of record — one platform, two access patterns.

## Current Reference Stack

| Layer | Component |
|---|---|
| Application | Databricks Apps (web UI / API) |
| Operational store | Lakebase (managed Postgres) — OLTP state, low-latency reads/writes |
| Analytical store | Delta Lake medallion under Unity Catalog |
| Sync | Lakebase ↔ lakehouse sync (reverse ETL / change sync) |
| Intelligence | Model Serving · Genie · SQL (called by the app) |
| Governance | Unity Catalog (analytical) + Lakebase roles; unified identity |

## When to use
- An interactive app needs low-latency reads/writes and transactional/session state.
- Operational data must round-trip with the governed lakehouse (write-back + analytics).
- The headline deliverable is the application experience itself.

## When NOT to use
- No operational/OLTP tier — a dashboard or Genie surface suffices → `arch_bi_genie_analytics`.
- The value is a GenAI/agent experience with no transactional tier → `arch_rag_agentic`.
- The build is a pipeline or a model, not an app → the ingestion/ML patterns.

## Common Variations
- App embeds a GenAI/agent surface → couples with `arch_rag_agentic`.
- App scores records inline → couples with `arch_ml_risk_scoring`.
- Fresh operational state from a stream → couples with `arch_streaming_cdc`.

## Platform Layers
| Layer | Databricks Product | Role |
|---|---|---|
| Govern | Unity Catalog · Lakebase roles | Analytical governance + operational access; unified identity |
| Store — OLTP | Lakebase (Postgres) | Low-latency app state, transactional reads/writes |
| Store — analytical | Delta Lake / UC tables | Governed system of record + analytics/ML |
| Sync | Lakebase ↔ lakehouse | Keep operational + analytical copies coherent |
| Intelligence | Model Serving · Genie · SQL | Endpoints the app calls |
| Experience | Databricks Apps | Interactive UI / API |

## Data Flow (Medallion)
| Stage | Processing | Example |
|---|---|---|
| Operational | App reads/writes to Lakebase (OLTP) | app_sessions, transactions |
| Silver/Gold | Synced into the governed lakehouse; conformed + aggregated | orders, daily_activity |
| Serving | Governed endpoints the app calls back into | scoring_endpoint, genie_room |

## Governance
Unity Catalog governs the analytical copy and any served endpoints; Lakebase enforces its own roles on
the operational tier. Identity is unified so app users map to governed access, and lineage covers the
sync between operational and analytical stores.

## WAF Alignment
- **Performance Efficiency** — Postgres-native OLTP for the app; lakehouse for analytics/ML.
- **Governance** — one governed analytical system of record behind the operational tier.
- **Reliability** — managed Postgres + coherent sync instead of a bolted-on external DB.
- **Production gap-fill (for IGs):** real auth/SSO, connection pooling + scaling, sync SLAs and
  conflict handling, backup/DR for the operational tier.
